# Следы падений

Где на планшете остаётся след паники ядра, сброса по сторожевому таймеру,
нехватки памяти и падения программы, и как их забирает `haltia-report`
(оболочка, haltia-de/shell). Issue
[#38](https://github.com/haltia-de/device-lenovo-b8000h/issues/38).

## pstore

Ядро пишет журнал в 1 МиБ памяти DRAM по адресу `0xbf500000` (ramoops,
патч 0049). LK и ядро эту память не трогают, и при тёплом сбросе
(перезагрузка, паника, сторожевой таймер) она не теряется. При потере питания
пропадает.

После загрузки записи видны в `/sys/fs/pstore/`. Файловую систему монтирует
initramfs, а если не смонтировал — служба OpenRC `sysfs`.

| Файл | Что в нём |
|---|---|
| `dmesg-ramoops-N` | Конец журнала ядра в момент oops или паники, до 32 КиБ на запись. Ядро пишет его само при падении. |
| `console-ramoops-0` | Последние 256 КиБ консоли ядра в прошлой загрузке. Есть после любого тёплого сброса, в том числе после зависания со сбросом по сторожевому таймеру, когда `dmesg-ramoops` не пишется. |

У записей есть ECC: повреждённая помечается, а не читается мусором.
Строка `pstore: backend (ramoops) writing error (-28)` значит, что запись не
поместилась. На ядрах до 0049 (7 КиБ SRAM) так и было.

После паники ядро перезагружает планшет через 10 секунд
(`/etc/sysctl.d/b8k-panic.conf`; у Alpine по умолчанию 120).

### Когда чистить

Записи лежат, пока их не удалят: `rm /sys/fs/pstore/<файл>` от root.
Следующая паника может взять то же имя, поэтому `haltia-report-root scan`
различает записи по имени и времени изменения (`name@mtime`). Сейчас оболочка
только читает записи и не удаляет их. Удалять стоит после того, как отчёт с
записью ушёл: иначе 1 МиБ заполнится, и ramoops начнёт перезаписывать самые
старые `dmesg`-записи. `console-ramoops-0` переписывается в каждой загрузке,
его чистить не нужно.

## Журнал ядра и syslog

- `dmesg`: кольцо на 128 КиБ (`LOG_BUF_SHIFT=17`). Счётчики MSDC
  (`B8K_REQDBG`, `B8K_IRQDBG`) и Wi-Fi заполняют его за несколько часов.
- `/var/log/messages`: busybox `syslogd`, 200 КБ и один старый файл.
  `klogd` пересылает туда сообщения ядра уровня warning и выше
  (`/etc/syslog.conf`): убийства OOM-киллера ядра (`invoked oom-killer`,
  `Out of memory: Killed process`), `WARNING:` с трассой, ошибки драйверов.
  Счётчики уровня info туда не идут.
- `earlyoom` пишет, какой процесс закрыл, через `logger` (`daemon.info`), то
  есть тоже в `messages`.
- `supervise-daemon` пишет туда же, когда служба падает по сигналу
  (`terminated by signal 11`).
- Падение процесса пользователя по сигналу: оболочка включает
  `kernel.print-fatal-signals=1` (`sysctl-haltia.conf`), и ядро пишет PC, адрес
  ошибки и регистры. Это уровень info, поэтому строки есть только в `dmesg`.
  `haltia-report` сохраняет строки падений из всего `dmesg`.

## Сторожевой таймер

- `mtk_wdt` сбрасывает через TOPRGU с `EXRST_EN` (`b8k-wdt-exrst`). После
  такой перезагрузки в `/proc/cmdline` стоит `boot_reason=4`.
- Службы, которая открывает `/dev/watchdog`, нет, поэтому при полном
  зависании планшет сам не перезагружается. Нужно держать кнопку питания.
- Сохраняется ли DRAM при таком сбросе через PMIC, не проверено. Если
  сохраняется, след в `console-ramoops-0`.
- Тестовое ядро 28 (PR #54) включает `MAGIC_SYSRQ` только через
  `/proc/sysrq-trigger`, для проверки:

  ```
  echo c > /proc/sysrq-trigger      # от root: паника
  # после перезагрузки:
  ls -l /sys/fs/pstore/
  ```

## Что собирает `haltia-report`

`haltia-report-root` (оболочка) читает и ничего не пишет:

- `scan` — строки OOM из `dmesg`, имена записей pstore, строки отката
  обновлений и упавшие службы из `messages`;
- `sections` — `dmesg`, журналы `/var/log` (`haltia-*.log`, `messages`,
  `rc.log`, `dmesg`), каждую запись pstore (до 64 КиБ), журнал обновлений.
